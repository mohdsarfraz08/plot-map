# Stage 3B.3C — Legacy Strategy Removal & Generic Migration Plan

## 1. Objective

Move from the current transitional architecture:

```text
ArchitecturalAnalysis
        │
        ├── Generic Path A ──────────┐
        │                            │
        └── Legacy Path B ───────────┤
                                     ↓
                              DesignStrategy[]
```

to:

```text
ArchitecturalAnalysis
        │
        ↓
Generic Data-Driven StrategyGenerator
        │
        ↓
DesignStrategy[]
```

The purpose is **not simply to delete old code**.

The purpose is to prove that everything useful encoded in the old archetype system can now be represented through the new data-driven analysis contract.

---

# 2. First principle

### Do NOT start by deleting the legacy code.

First perform:

```text
Legacy behavior
      ↓
Identify architectural knowledge
      ↓
Represent knowledge as data
      ↓
Generate equivalent strategies generically
      ↓
Compare outputs
      ↓
Delete legacy path
```

This protects us from accidentally losing architectural intelligence.

---

# 3. Audit the existing legacy path

Inspect the current legacy section of:

```text
backend/app/services/analysis/strategy_generator.py
```

Identify every architectural concept currently encoded there.

For example, from the previous audit:

```text
VERTICAL_CIRCULATION
ENTRANCE_STRATEGY
UNIT_ORGANIZATION
FLOOR_ALLOCATION
shared
independent
hybrid
privacy
circulation
service core
```

For every legacy rule, classify it as:

### A. Data already represented

Can already be expressed using:

```text
DecisionRecord
alternatives
IncompatibilityRule
DimensionRelationship
ConflictRecord
Preference
Constraint
Objective
```

→ migrate directly.

### B. Missing data contract

The legacy system knows something important that the new schemas cannot express.

→ **do not hardcode it into the generic generator.**

Instead, identify the missing schema capability.

### C. Presentation-only behavior

Things such as strategy naming or rationale formatting.

→ can be regenerated generically or simplified.

### D. Obsolete behavior

Behavior that should not survive in the new architecture.

→ deliberately remove.

---

# 4. Reconstruct the benchmark through data

The original benchmark is important:

```text
44 ft × 42 ft
four-family scenario
multiple possible floor/circulation arrangements
```

But we must NOT encode:

```text
44
42
four families
```

inside the generator.

Instead, construct an `ArchitecturalAnalysis` that describes the scenario.

For example conceptually:

```text
Decision:
    vertical_circulation
    alternatives:
        shared
        independent
        hybrid
```

Another:

```text
Decision:
    floor_allocation
    alternatives:
        grouped
        distributed
```

And relationships/conflicts where appropriate.

The exact representation must come from the existing schemas and documented architecture—not assumptions.

---

# 5. Golden behavior test

Create a migration test that compares the old and generic approaches **before deleting the old implementation**.

The objective is not necessarily:

> outputs must be byte-for-byte identical.

Instead verify semantic equivalence for the behaviors that matter:

```text
✓ required decision dimensions preserved
✓ alternatives represented
✓ hard constraints respected
✓ explicit conflicts respected
✓ relationships preserved
✓ preferences preserved
✓ objectives preserved
✓ uncertainties preserved
✓ deterministic output
✓ strategy count remains bounded
```

If the old system produces three meaningful architectural alternatives, the new system should be capable of representing those alternatives through data.

---

# 7. Critical test: zero legacy knowledge

This is the most important acceptance test.

Create an analysis containing only:

```text
custom_dimension_a
    A
    B

custom_dimension_b
    X
    Y
```

The generator should produce:

```text
A + X
A + Y
B + X
B + Y
```

Then add:

```text
Incompatibility:
A + Y
```

The result should become:

```text
A + X
B + X
B + Y
```

No architectural vocabulary is involved.

That proves the engine is genuinely generic.

---

# 8. Remove legacy fallback

Only after all migration tests pass:

Remove:

```text
legacy archetype generation
legacy circulation strategy generation
legacy hardcoded trade-off generation
```

The final `generate_strategies()` path should have **one strategy-generation mechanism**.

No:

```python
if alt_map:
    generic()
else:
    legacy()
```

remaining.

# 11. Acceptance criteria

3B.3C is complete only when:

### Genericity

```text
Unknown dimension → works without code change
```

### Legacy removal

```text
Legacy archetype code → removed
```

### Benchmark

```text
44×42/four-family → works through data-driven path
```

### General scenario

```text
Different residential scenario → works
```

### Unknown scenario

```text
Completely custom dimensions → works
```

### Constraints

```text
Hard constraints → never intentionally violated
```

### Compatibility

```text
IncompatibilityRule → correctly filters combinations
```

### Relationships

```text
DimensionRelationship → preserved/converted into strategy trade-offs
```

### Determinism

```text
same input → same output
```

### Bounds

```text
candidate combinations ≤ 100
strategies ≤ 10
```

### Architecture

```text
No geometry
No solver
No LLM
No API integration
```

# 13. Recommended execution sequence

I would give Antigravity the work in **four small phases**, rather than asking it to delete everything in one shot:

```text
3B.3C-1 ✅
Legacy audit
     ↓
3B.3C-2 ✅
Represent missing legacy knowledge as data
     ↓
3B.3C-3 ✅
Golden/migration tests
     ↓
3B.3C-4 ✅
Remove legacy implementation
```

This is much safer than:

```text
"Delete the old strategy code and make tests pass."
```

because that could produce a superficially green implementation while silently losing architectural behavior.
